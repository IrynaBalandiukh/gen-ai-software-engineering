# Specification — Multi-Agent Banking Transaction Pipeline

> Generated by the `write-spec` skill. Sources of truth: `CLAUDE.md` (primary)
> and `sample-transactions.json` (real input). Every rule, threshold, filename,
> and function signature below is drawn from those sources.

---

## 1. High-Level Objective

Build a TypeScript multi-agent pipeline that ingests raw JSON transactions and runs each through validation, fraud screening, compliance checks, and settlement, then aggregates every outcome into a single pipeline summary report written under `shared/results/`.

---

## 2. Mid-Level Objectives

- **Validation & monetary handling:** reject malformed transactions (missing required fields, non-ISO-4217 currency such as `XYZ` in TXN006, zero amount) using `decimal.js` for every amount — never JS `number`/float; a negative amount is accepted **only** when `transaction_type === "refund"` (TXN007's `-100.00` refund passes), and is rejected with reason `"negative amount not allowed for non-refund transaction"` otherwise, while a zero amount is rejected with `"amount must be non-zero"`.
- **Fraud review threshold with risk score:** compute an integer risk score in **0–3**, adding **+1** for each present signal — high value (absolute amount `> $10,000`), unusual timing (UTC hour `00:00`–`05:00`), and cross-border (`metadata.country !== "US"`) — and **flag for fraud review** whenever the high-value signal is present (e.g. TXN002 at `25000.00` and TXN005 at `75000.00` are flagged; TXN004 in DE at `02:47Z` scores 2 but is not flagged).
- **Compliance regulatory reporting:** on any transaction `> $10,000`, set `requiresRegulatoryReport: true` on the message — a regulatory flag distinct from the fraud risk score.
- **Settlement:** compute the settled amount with `decimal.js` using `ROUND_HALF_UP`, set the final status, and never settle an already-rejected transaction.
- **Rejected results & final landing:** every rejected transaction is written to `shared/results/` with a human-readable **`reason`** field; all final accepted/rejected outcomes land in `shared/results/`, and the Reporting Agent aggregates them into the pipeline summary.
- **Audit logging:** every agent operation logs an **ISO 8601 / UTC timestamp**, the **agent name**, the **transaction id**, and the **outcome**, while treating account numbers and names as PII (never logged in plaintext).

---

## 3. Implementation Notes

- **Language & runtime:** TypeScript on Node.js 20+, ESM modules; orchestrator entry is `npx tsx main.ts` / `npm run pipeline`.
- **Monetary type & rounding:** use `decimal.js` for all amounts; settlement rounds with `ROUND_HALF_UP`. Never use JS `number`/float for money.
- **Currency validation standard:** currency codes must be valid **ISO 4217** (USD, EUR, GBP, JPY, …); unknown codes (e.g. `XYZ`) are rejected.
- **Negative- and zero-amount handling:** negative amount valid only for `transaction_type === "refund"` (reason `"negative amount not allowed for non-refund transaction"` otherwise); zero amount always rejected (`"amount must be non-zero"`); all other amounts must be positive.
- **Home country / cross-border:** the bank's home country is **US**; cross-border means `metadata.country !== "US"`.
- **Unusual-timing window & risk-score scheme:** unusual timing is a transaction hour in **UTC** between `00:00` and `05:00`; risk score is an integer **0–3**, +1 each for high-value (`> $10,000` on absolute amount), unusual timing, and cross-border; fraud flag is raised when the high-value signal is present.
- **Compliance flag:** transactions `> $10,000` set `requiresRegulatoryReport: true`, separate from the fraud risk score.
- **Audit-trail contents:** each log entry carries an ISO 8601 timestamp, the agent name, the transaction id, and the outcome.
- **PII handling:** account numbers and names are sensitive — mask or omit them; never log them in plaintext, and keep them out of commits and screenshots.
- **Message protocol:** agents communicate via JSON message files passed through `shared/{input,processing,output,results}/`; each agent rewrites `source_agent` to itself and `target_agent` to the next hop derived from the pipeline order (do not hardcode the next agent).
- **Test framework, coverage target & hard gate:** Vitest + `@vitest/coverage-v8`; coverage **target ≥ 90%** with a **hard gate at 80%** enforced by a git `pre-push` hook (push blocked below 80%).

## 4. Context

### Beginning context

- `sample-transactions.json` — 8 raw transaction records (TXN001–TXN008), including the edge cases: high-value wire (TXN002, TXN005), cross-border + unusual timing (TXN004), invalid ISO 4217 currency (TXN006), and the negative refund (TXN007).
- Empty `shared/{input,processing,output,results}/` directories.
- `CLAUDE.md` — project context and business rules.

### Ending context

- `shared/results/` populated with one final outcome (accepted/rejected, with `reason` for rejections) per transaction.
- A pipeline summary report produced by the Reporting Agent (feeding the MCP `pipeline://summary` resource).
- The pipeline agent modules under `agents/` (`transactionValidator.ts`, `fraudDetector.ts`, `complianceChecker.ts`, `settlementProcessor.ts`, `reportingAgent.ts`).
- The `main.ts` orchestrator wiring the run end to end.
- Vitest suites under `tests/` at the target coverage (≥ 90%, hard gate 80%).
